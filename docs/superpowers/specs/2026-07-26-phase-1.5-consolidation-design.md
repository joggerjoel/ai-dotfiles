# Phase 1.5 — Making the Memory Observable and Answerable

**Status:** Design approved, ready for planning
**Date:** 2026-07-26
**Follows:** [Phase 1 capture path](2026-07-26-whatsapp-relationship-memory-design.md)
**Precedes:** Phase 3 — the query surface (call / SMS / app)

## Goal

Three changes that turn a working capture pipeline into a system its users can
see working.

Move the bot's tables into the `voice` database so they sit beside
`person_contacts`, and reconcile the two so identity resolution starts from
1,738 real contacts instead of an empty table. Then start recording the two
participants themselves, so questions about each other have an answer. And close
the feedback loop: acknowledge every capture, treat `@bot` as a question rather
than something to extract, and answer the questions plain SQL can answer.

The third is the one that changes the experience. Phase 1 captures correctly and
says nothing, which is indistinguishable from being broken. Every verification so
far has needed server logs read over SSH — a method that does not survive this
conversation.

## Why this is its own phase

The original ask — "ask it questions about Jo and myself by call, text, or app" —
is two projects. Retrieval needs embeddings, and `people.embedding` was
deliberately dropped from Phase 1 because string resolution needed no vectors.
Specifying a query layer against a schema that is still moving would mean
rewriting it once the schema settles. Phase 1.5 settles the schema.

## Scope

**In scope**

- Move the `prmm` tables into the `voice` database under a dedicated schema
- Link `prmm.people` to `public.person_contacts` without writing to it
- Record the two participants as people, and capture what they say about
  each other
- Give the extractor the participants' names, which it currently lacks
- Acknowledge captures with a reaction, so the system is visibly alive
- Gate `@bot` mentions as questions instead of extracting them
- Answer the relational questions — where met, last spoken, what is known,
  who works where — with SQL

**Out of scope**

- Embeddings and semantic search — Phase 2
- Voice, SMS, and app surfaces — Phase 3. This phase answers in WhatsApp only.
- Proactive nudges and the trigger scheduler — Phase 2
- Writing to `person_contacts`. The bot reads it and points at it. That table
  belongs to a live platform.

## What already exists

`voice` is a production care-coordination platform on aorus4: roughly sixty
tables across several verticals, 68 real calls, its own `schema_migrations`.

Two of its tables matter here:

| Table                        | Rows  | Relevance                                                                                                                                                             |
| ---------------------------- | ----- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `person_contacts`            | 1,738 | A populated contact table — every row owned by `joel.labelle@gmail.com`, sourced from conferences. Carries phone, email, company, title, LinkedIn, `conference_year`. |
| `contact_circle_memberships` | 1,737 | An existing grouping layer over those contacts.                                                                                                                       |

`caller_facts` exists and is empty; the concept was anticipated and never used.

Phase 1 built `people` from zero while this sat one container away. Unlike
OpenBrain — read-only, someone else's — this database is ours, on our host, with
our email on every row. Integration is available here in a way it was not there.

## Decisions

| Decision                    | Choice                                                | Rationale                                                                                     |
| --------------------------- | ----------------------------------------------------- | --------------------------------------------------------------------------------------------- |
| Location                    | `prmm` schema inside the `voice` database             | Same database enables joins; a separate namespace prevents collisions with ~60 growing tables |
| Migration flow              | Our own numbered files, not their `schema_migrations` | Their table has one row; entangling release cycles buys nothing                               |
| Person link                 | `prmm.people.person_contact_id` → `person_contacts`   | Resolution gains 1,738 candidates without the bot ever writing to a production table          |
| Participants                | Recorded as people, flagged `is_participant`          | Required for "what did Jo say about the trip?" to have an answer                              |
| Private about a participant | Allowed, but announced at capture                     | See Consent below                                                                             |
| `prmm-db` container         | Torn down; no data migration needed                   | It holds zero rows — the only writes were a smoke test that cleaned up after itself           |
| Capture acknowledgement     | Emoji reaction on the source message                  | Visible proof without the bot talking in the room                                             |
| `@bot` handling             | Mention gating, routed away from capture              | Today the mention itself would be extracted as a contact named after the bot                  |
| Answering                   | SQL over relational columns                           | "Where did I meet Jo" is a column lookup; only fuzzy recall needs Phase 2 vectors             |

### Why a schema, not `public`

Dropping eight tables into a sixty-table `public` schema risks a collision every
time either project adds one. A named schema costs one line, keeps ownership
legible, and makes uninstall a single `DROP SCHEMA prmm CASCADE`. Joins across
schemas in one database are free.

### Why not write to `person_contacts`

It is a live table the voice platform reads. A bad extraction writing into it
would corrupt production data belonging to another system, and the blast-radius
argument that moved us off OpenBrain applies unchanged. The bot creates its own
row and points at theirs.

## Architecture

```
  voice database (aorus4)
  ├── public                        owned by the voice platform
  │     person_contacts  (1,738)    ← read, never written
  │     contact_circle_memberships
  │     callers, calls, caller_facts
  │
  └── prmm                          owned by this project
        people ──person_contact_id──┘
        memories, memory_people, interactions,
        triggers, clarifications, resolution_log, write_ops
```

The bot's only change is its connection string and a `search_path`. Every
repository method keeps its signature; `PgRepository` is the sole file that
learns about the join.

## Identity reconciliation

`findPeople` returns bot-known people **plus** matching `person_contacts` rows,
mapped into the same `KnownPerson` shape. Resolution then scores against both.

The extra columns are extra signal, not just extra rows: `company_name`, `title`,
`email` and `phone` all discriminate between people who share a first name.
`scoreCandidate` currently reads `company` alone; it gains real leverage here.

When resolution matches a `person_contacts` row that has no `prmm.people`
counterpart, the bot creates one carrying `person_contact_id`. The contact row is
untouched.

**Expect the ask-rate to rise.** Against 1,738 contacts, "Sarah" is ambiguous far
more often than it was against an empty table. The cautious bands and the DM
clarification channel were built for this, and `resolution_log` will show whether
the thresholds need tuning. A short noisy period is the correct behaviour, not a
regression.

## Recording the participants

Three changes, and the first is the one that makes the rest possible.

**The extractor cannot currently attribute anything to a participant**, because
the transcript labels speakers by phone number and the prompt has no idea whose
number is whose. The prompt gains a participant roster — `+1718…: Joel`,
`+1551…: Jo` — and the rule inverts: record participants when they are discussed,
and use their names rather than their numbers.

**`prmm.people` gains `is_participant BOOLEAN`** and is seeded with a row per
user, each linked to a `person_contacts` row where one exists.

**`05-participant-not-a-person.json` is rewritten.** It currently asserts that a
participant's own birthday must not become a person record, which is now exactly
backwards. The replacement asserts the opposite, and a new fixture keeps the
original protection where it still holds: a bare phone number with no name
attached must never become a person.

## Consent

Once the participants are subjects, a DM can hold a private memory _about the
other participant_ — something one user tells the bot about the other, in a
memory they otherwise share.

**This is allowed, and announced.** When a DM capture resolves its subject to the
other participant, the bot replies naming what it stored and who cannot see it:

> Noted privately about Jo. Jo won't see this.

Refusing the capture outright would break the channel's most valuable use — "Jo
has been stressed about work, remind me to check in gently" is caring, not
surveillance. Storing it silently would make the channel a trap, which is the
failure the whole visibility design exists to prevent. Announcing it is the same
answer the rest of the system already gives: `degraded` rather than a false
`stored`, a loud `unresolved-sender` rather than a quiet drop, an explicit ask
before promoting a private fact to shared.

`PRMM_ALLOW_PRIVATE_ABOUT_PARTICIPANT=false` refuses these captures instead, for
operators who want the harder line.

**This design records a relationship between two people, one of whom is not in
the room when it is configured.** Jo should know the bot records what is said
about her, that DM content is private to its author, and that she has the same
channel. That is a conversation, not a config flag.

## Feedback and answering

### Acknowledgement

The bot reacts to the message that produced a capture. No text, no thread noise:

| Outcome | Reaction |
| --- | --- |
| `stored` | 📌 |
| `degraded` — writes queued, not persisted | ⚠️ |
| a clarification was raised | ❓ |
| `skipped` by the relevance gate | none |

Silence on a skip is deliberate: reacting to every "ok" would be worse than
saying nothing. A capture that lands must be visible, because a correct system
and a dead one currently look identical from inside the group.

`InboundMessage` carries only `id` today; reactions need the full Baileys message
key, so `normalizeMessage` starts preserving it.

### Mention gating

A message addressed to the bot is a question, never a capture. Gating happens in
`routeMessage`, before the buffer, so a mention never enters a batch.

This is the same defect class as `@lid` senders and BIGINT-as-string: an input the
system cannot classify falls through to the default path. Here that path is
extraction, so today `@bot, where did I meet Jo?` would try to create a person
named after the bot.

### Answering

Four intents, matched against the question text, one query each:

| Intent | Source |
| --- | --- |
| where did I meet X | `people.first_met_context`, `people.first_met_at` |
| when did I last speak to X | `interactions.occurred_at`, newest first |
| what do I know about X | `memories` joined through `memory_people` |
| who do I know at Y | `people.company` and `person_contacts.company_name` |

Subject resolution reuses `scoreCandidate` — the same identity logic as capture,
so "Sarah" is ambiguous in a question for the same reasons it is ambiguous in a
capture, and the answer says so rather than guessing.

Anything unmatched gets an honest refusal naming what the bot *can* answer. A
silent non-response is the failure this section exists to remove.

Visibility is enforced on read: a question from one user never surfaces the
other's private memories.

## Error handling

| Failure                                     | Response                                                                      |
| ------------------------------------------- | ----------------------------------------------------------------------------- |
| `person_contacts` unreadable                | Park the batch. Resolving against a partial roster would duplicate people.    |
| `person_contact_id` points at a deleted row | `ON DELETE SET NULL`; the `prmm.people` row survives with its memories intact |
| Participant roster missing a user           | Fail at config load, as `loadConfig` already does for malformed ids           |
| Migration partially applied                 | Wrap in a transaction; Postgres DDL is transactional                          |
| Reaction send fails                         | Log and continue; a missing ack must never fail a committed capture           |
| Question subject ambiguous                  | Answer with the candidates rather than picking one                            |
| Question about a person with no memories    | Say so plainly; an empty answer reads as a failure                            |

## Testing

- Resolution against a `person_contacts` fixture: exact name, shared first name
  disambiguated by company, and a contact with no bot-side row
- Participant capture: a memory about the other participant resolves to their
  seeded person row rather than creating a duplicate
- Visibility: a DM memory about the other participant stores `private` and
  returns the announcement; with the flag off, it refuses
- The rewritten fixture pair — participant _is_ recorded by name, bare phone
  number is _not_
- A mention never reaches the capture buffer, and never creates a person
- Each of the four intents against a seeded database, plus the unmatched
  fallback naming its own capabilities
- A question from user A never returns user B's private memories
- Integration against the real `voice` database, since the last two defects found
  in this project were both invisible to mocks

## Prerequisites

1. **Confirm the migration window.** `voice` serves a live platform. The DDL is
   additive and namespaced, but it should still land when nothing is mid-call.
2. **Decide the participant roster's source of truth.** Names come from config
   today; they could come from `person_contacts` rows instead.
3. **Talk to Jo.** See Consent.
